# A/B 非劣闸门实测证据：V1 圆桌（入口 A）vs V2 协作引擎（入口 B）

> 日期：2026-10-01 ｜ 模型：`deepseek-chat` ｜ 样本：同一话题重复 3 次 ｜ 总花费：**$0.013092**
> 复现：`python benchmarks/ab_gate.py --real --repeats 3`（需 agent-roundtable-mcp（入口 A）检出：`--v1-root`）

## TL;DR

- 固定话题、固定人格、同一模型下：**V2 平均贵 1.33×，盲评质量高 +2.83/25**。
- 既定闸门「**不能同时更贵且更差**」在 3/3 次重复中**通过**（V2 从未同侧失败）。
- 但「同等 token 办更好的事（省 token）」在这份样本里**没有被证明**；证据支持的是「多花约三成换到更可执行的结果」。
- ⚠️ 顺带实测出一个更要紧的问题：**引擎自报的 token/成本只覆盖真实 API 用量的一半**——每个任务的经理裁决（仲裁）LLM 调用完全没被记账，见 §5。

## 1. 为什么测

项目既定决议：V2 的价值主张是「用受控 token 办更好的事」，成立与否取决于「省下的冗余 token > 多花的协调 token」；
因此合并/发布前必须有一份对 V1 基线的 A/B 实测，且必须能证明「不是更贵且更差」——而不是只靠 README 里的说法。
本轮（2026-10-01，用户授权真机运行）产出首份证据。

## 2. 方法

| 项 | 臂 A（基线） | 臂 B（V2） |
| --- | --- | --- |
| 入口 | V1 圆桌（会议）`run_roundtable` | V2 协作引擎（公司）`run_collab_sync` |
| 结构 | 3 位专家（computing/philosophy/history）× 1 轮 + 主持人提问 + 轮次小结 + 终稿 | 4 个任务：3 个 persona 产出 + 1 个汇总任务（`data_deps` 指向前三个），含硬规则审计 + 经理裁决 |
| 人格接地 | 原生人格卡（config/domain_experts） | 同一张人格卡文本写进 `task.input`（V2 无 persona 库，见 §6） |
| 语料 | 本 checkout 的 `knowledge/experts/*` 为空 → 检索无命中 | 无 RAG |
| 模型 | deepseek-chat，`max_tokens=900` | 同 |
| 计价 | 与 V2 同一张价目表 `collab.costing.price_tokens` | 同 |
| 真实用量 | 计数代理包裹 LLM 客户端，逐次累计 API 返回的 usage（不采信自报） | 同（同一代理注入引擎路径） |
| 判分 | 同模型盲评、5 维 × 1-5 分、**两次交换顺序**取平均 | 同 |

话题（双臂完全相同）：

> 一个开源的多 Agent 协作引擎目前已经跑通：任务分派、审计、仲裁、成本归属与报告。开发资源只有一个开发者、两周时间。下一步应该优先做哪三件事、砍掉什么？请给出明确的取舍、理由，以及可验证的验收标准。

## 4. 结论

1. **闸门通过**：V2 在 3 次重复里都没有出现「更贵且更差」。按既定判据这是合格线。
2. **但价值主张未被证明**：V2 平均贵 33%，质量高约 14%（相对）。当前证据支持的是用户可接受的「多 token、更好」，**不是**「同 token 更好」或「更省」。要主张后者需要更多样本与更低成本的协调路径。
3. **V2 的形状很清楚**：赢在「可执行性 + 结构」（把讨论变成带优先级的清单），输在「反方/风险视角」（V1 的圆桌天然带互驳）。这给优化方向：不该去堆更多角色，而该把「风险与反方」显式加进 V2 的产出契约。

## 5. ⚠️ 实测发现：引擎自报成本只覆盖约一半真实用量

同一批运行里，计数代理记到的真实用量与引擎自己在报告里写的数字对不上：

| 重复 | 真实 token | 引擎自报 token | 覆盖率 | 真实 USD | 引擎自报 USD | 覆盖率 | V2 LLM 调用次数 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 13296 | 6660 | **50.1%** | 0.002508 | 0.001210 | 48.2% | 10 |
| 2 | 10476 | 5072 | **48.4%** | 0.001989 | 0.001214 | 61.0% | 8 |
| 3 | 9884 | 4781 | **48.4%** | 0.001863 | 0.001131 | 60.7% | 8 |

调用次数对得上：4 个任务 = 4 次执行 + 4 次经理裁决 = 8 次（rep1 的 10 次含一次打回重试）。
而引擎报告只算了那 4 次执行。

**代码定位（根因）**

- 执行节点在 `llm.generate()` 之后立刻读 `last_usage` 并计价，写进该任务的 audit：`collab/graph.py` 执行节点（`content = llm.generate(prompt)` 之后紧接 `usage = getattr(llm, "last_usage", None)` → `cost_usd = price_tokens(...)`）。
- 仲裁节点对每个 DONE 任务调用 `manager_arbitrate(audit_llm or llm, task, audit, root_dir=root_dir)`（`collab/graph.py` 仲裁节点），`manager_arbitrate` 内部是一次真实 LLM 调用（`collab/arbitration.py`）。
- 这次调用的 usage **既没有写进 `attempts`，也没有写进 `results`/`state`**；而报告与成本统计只汇总 `results`（`collab/costing.py: cost_summary`）。
- 结果：报告里的「Token 总消耗 / 成本(USD)」不是「总」，而是「任务执行部分」。

**影响（为什么这不是小事）**

1. 报告低估真实 API 花费约 **50%**；
2. 被漏掉的恰恰是**协调费（经理/仲裁）**——正是 V2 宣称要显性化、并用来判断「这次协作值不值」的那一项；
3. FR-ECO-3 的全局预算闸门用的是 `token_total`（只含执行），因此预算判断同样偏低；
4. A/B 的对价关系若用引擎自报数字算，会**系统性偏向 V2**（少算自己 50% 成本）。本证据用的是代理计数，故 §3 的双臂对比不受此影响。

**建议修法（最小改动，不破坏按 persona 拆分）**：在仲裁节点把 `manager_arbitrate` 前后包一层 usage 采集，
把「协调 token / 协调成本」作为**独立字段**记入 state 与 run 摘要（不要摊到 persona 上，避免污染归属），
报告里改成「任务执行成本 + 协调开销 = 实际 API 成本合计」，并让预算闸门读合计值。

## 6. 次要发现：V2 的 persona 目前只是标签

`collab/persona.py` 的 `persona_hint()` 直接返回 `persona_id`（有意保持零依赖，注释里也写明「等引入 V2 自己的 persona 格式再扩展」）。
所以 V2 的「跨 persona 协作」在提示层没有真正接地。本次为公平起见，把同一张人格卡文本写进了 `task.input`；
若想让 V2 独立成立，应让 `persona_hint` 能读 `root_dir` 下的 persona 配置（或 V2 自己的 personas 文件）。

## 7. 局限（请勿过度解读）

- **单一话题**、n=3；话题本身与本项目相关（自我指涉）。
- 判分器与双臂同族模型（deepseek-chat），分数是「LLM 偏好」的代理，不是业务结果；判分器位置偏差已用换序平均抵消，但样本太小，±1 分（合计 25 分制）内的差异不可区分。
- V1 臂带 RAG 通道但本 checkout 语料为空；若 V1 装了语料，天平会向 V1 倾斜，本结论只对「无语料」成立。
- V2 臂走 `run_collab_sync`（与 CLI worker 同图，仅去掉线程/心跳/持久化封装），未走 `run_collaboration` 的异步外壳。
- 成本口径为 V2 自己的价目表（deepseek 家族价），不是账单实付。

## 8. 下一步建议（按优先级）

1. **P0：修成本归属缺口**（§5）——这是「成本透明」承诺的地基，也是 A/B 对价比较的前提。
2. **P1：让 persona 真正接地**（§6），否则「跨 persona」是提示词装饰。
3. **P1：把「风险/反方」写进产出契约**（§4 的失分点），而不是增加角色数量。
4. **P2：扩样本**（多话题 × n≥5，并记录判分器自一致性）后再谈「省 token」的价值主张。
