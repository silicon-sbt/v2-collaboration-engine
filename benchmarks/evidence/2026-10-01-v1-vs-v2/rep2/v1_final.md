## 主要共识

1. **优先级应从“增加功能”转向“建立可追责的可靠性闭环”**  
   三方在实质上收敛为一组基础设施要求：同一输入可重放；结论可回溯到具体 Agent、证据与规则；失败能落到明确责任主体，而不是笼统归因于“系统行为”。

2. **当前阶段应明确砍掉四类功能**  
   可视化面板、插件市场、多模型适配层、复杂权限体系。三方均认为这些属于“看起来完整”的过度设计，容易在单人两周约束下挤占核心可靠性建设。

3. **砍掉上述功能后的风险控制方式基本一致**  
   用 CLI、结构化日志、回放机制兜底；等真实用户暴露需求后，再决定是否补可视化、插件、多模型或权限能力。

4. **前 3 件事的候选范围已经收敛**  
   主要集中在：确定性回放与审计闭环；责任与成本归属闭环；仲裁失败注入、矛盾降级与复核路径。分歧不在“要不要这些方向”，而在“正当程序/复核路径是否必须进入前 3，以及如何最小化实现”。

## 主要分歧

1. **回放是否足以构成“正确性”**  
   - Computing 立场：回放与故障注入是可验证的工程底线，先保证可复现、可观测、可回滚。  
   - Philosophy 立场：回放只回答“发生了什么”，不回答“凭什么算对”；仲裁前申诉/复核与降级程序必须进入前 3。  
   - History 立场：回放、责任链、正当程序缺一不可，但历史类比只能作为警示，不能直接当作当前需求证明。

2. **“仲裁正当程序/复核路径”是否会在两周单人约束下挤占工程预算**  
   这是第 1 轮留下的核心追问。需要把 Philosophy 主张的“复核单/降级触发”拆成最小可验收实现，并判断其依赖顺序与失败模式。

3. **“一致率 100%”在模型非确定性下是否成立**  
   讨论中已提出应确认：是否应改为“可解释差异率 0%”或“差异必须可归因”。否则，若模型本身存在非确定性，机械要求 100% 一致可能不可验证，或会把工程目标带向错误方向。

## 最有价值观点

1. **Computing 的工程底线观点**  
   当前“跑通”只是 demo 级能力，不等于可靠生产能力。瓶颈不是加功能，而是失败模式可观测、可复现、可回滚。确定性回放、故障注入、单命令端到端冒烟，是可验证的工程基础。

2. **Philosophy 的价值主张观点**  
   多 Agent 协作引擎的核心价值不是“多个 Agent 看起来能协作”，而是让多个 Agent 的判断可被追责。没有决策理由留痕、责任可归属、分歧正当程序，系统就不成立。

3. **History 的历史类比观点**  
   Unix 管道靠“可组合+可追责”活下来，许多“智能工作流平台”死在可视化与插件生态的过早扩张。历史类比不能直接证明当前路线，但能警示：别把“平台化”当早期基建，那通常是权力尚未定型前的伪需求。

4. **三方收敛出的最小闭环**  
   同一输入可重放；每条结论可回溯到 Agent、证据、规则；任一失败能落到具体 Agent 与预算项；矛盾结论必须触发降级并生成可读复核单，不得静默合并。

## 风险提示

1. **若只做回放，可能遗漏“正当性”问题**  
   系统可以证明“发生过什么”，但不能证明“为什么这个仲裁结论可被接受”。在需要问责、审计或对外解释的场景中，这会成为结构性缺陷。

2. **若强行加入完整复核路径，可能挤占两周预算**  
   单人两周内，完整申诉、复核、降级、复核单体系可能过重。必须拆成最小可验收功能，否则会拖垮回放与责任归属的基础建设。
